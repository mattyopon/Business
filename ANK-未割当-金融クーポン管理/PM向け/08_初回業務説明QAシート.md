# PM-08. 初回業務説明 QA シート (14:00 〜)

**目的**: 初回業務説明の場 (顧客 / 元請 PL 同席想定) で **これだけは絶対に持ち帰りたい** 全体像と前提を、限られた質疑時間 (15-30 分想定) で確実に取りに行くための質問リスト。  
**粒度方針**: 後続の要件定義ヒアリング (`業務用/10_要件定義/10-4_ヒアリングシート.md` の 80+ 問) でカバーできる **詳細パラメータは今日は聞かない**。今日聞かないと後で困る **全体地図・関係者・連絡ルート・スケジュール前提** だけに絞る。

---

## 0. 使い方

- 説明中は **メモに集中** し、説明後の質疑タイムで本リストを開く
- Must (★) → Should (◯) の順で聞く。時間切れなら Should は別途メール / 次回会議で
- 答えが「今は未確定」「PF 側次第」だった場合は **未確定事項管理表に即起票** (回答そのものが情報になる)
- 質問は **「自分が今後動くために必要」** という形で言い回し、評価のための質問に聞こえないよう注意

---

## 1. Must 質問 (★、10 問、目安 15-20 分)

> 本案件は **オンプレ→AWS リフトアンドシフト** + **完全プライベート業務系** + **VPN/閉域網作業** + **行内独自統制多数** + **参画まで資料受領が限定的** という前提のため、初回業務説明では特に **(a) 既存システムの実態**、**(b) 作業環境・端末**、**(c) 行内独自統制** を最優先で押さえる。


### Q0. ★ 既存システム (オンプレ稼働中のクーポン管理) の現状と保守体制
- **聞きたいこと**: (a) 既存システムの稼働開始時期と現行アーキ概要 (b) 既存保守ベンダーの会社名・担当者・連絡方法 (c) ソースコード / 設定値 / 運用 Runbook の入手可否と窓口 (d) 既存環境のテスト環境利用可否
- **なぜ今**: リフトアンドシフトの成否は既存挙動の完全把握にかかる。Day-7 までに既存保守側と週次同期を組まないと、要件定義の全工程が空転する
- **想定回答例**: A. 既存ベンダーが継続保守、月次同期可 / B. 既存ベンダー撤退、ソースは入手済 / C. ベンダー連絡未確立、顧客主担当経由で要請中

### Q1. ★ 既存 PM (現要件定義工程 1 名在籍) との役割分担・引継ぎ
- **聞きたいこと**: 既存 PM の方は要件定義 Exit まで継続? 自分はサポート? 主担当交代?
- **なぜ今**: 自分の役割が「主」か「副」かで来週からの動きが全く変わる
- **想定回答例**: A. 既存 PM は Exit まで主担当、自分は SA 寄り / B. 自分が主担当を引き継ぎ / C. 共同体制

### Q2. ★ 顧客側の意思決定者 (要件確定 / 予算 / スコープ変更)
- **聞きたいこと**: それぞれ別の方か同一か。何かを決めるとき誰に最終承認をもらうか
- **なぜ今**: ここが曖昧だと後続ヒアリングで往復が発生する
- **想定回答例**: 主担当 (実務窓口) ↔ 部門長 (意思決定) ↔ CIO (予算・スコープ) の三層など

### Q3. ★ 顧客側の主管部門と関係部門 (販促企画 / IT 統括 / 監査 / 運用)
- **聞きたいこと**: 自分が日常コミュニケーションすべき部門・担当者の連絡先一覧
- **なぜ今**: 今日もらえないと来週初動でロスする
- **メモ欄**: 部門名 / 担当者 / 連絡手段 (メール / Slack / Teams) を表で

### Q4. ★ 次期クラウド共通基盤 (オープン勘定系 PF) の PoC 現状とガイドライン提供タイミング
- **聞きたいこと**: (a) PoC は今どこまで進んだ (b) ガイドラインが提供されるイベントの **時期・名称・対象範囲** (c) 確定情報はいつ揃う見込みか
- **なぜ今**: 要件定義 (2026/4-12) の前提条件。受領タイミングを知らないと先行可能タスクの仕分けができない
- **想定回答例**: 「Q3 中に v1.0、Q4 中に v2.0」「○月の中間レビューイベントで提供」「PoC 完了は YYYY-MM 想定」など

### Q5. ★ PF 側との連絡窓口と会議体
- **聞きたいこと**: PF 側責任者 + 主担当 + 連絡頻度 (週次 / 月次)、既存の会議体があるかどうか
- **なぜ今**: ガイドライン受領 → 影響分析 → 顧客合意の 2 週間サイクルを回す体制を組む必要があるため

### Q6. ★ 親システム (全店名寄せ / 顧客名寄せ) との連携方式の方針
- **聞きたいこと**: (a) 親システム責任者・主担当 (b) 連携方式 (バッチ / API / 未確定) (c) I/F 仕様確定見込み (d) 親システム側テスト環境利用予約方法
- **なぜ今**: 結合試験 (2027/10-) スケジュールの逆算に影響する最大の依存先

### Q7. ★ 監査部門・セキュリティ部門との接続
- **聞きたいこと**: (a) 監査責任者は誰 (b) FISC 第 11 版対応の他システム実績 (c) 既存 SOC (Splunk 等) の有無 (d) 月次レビュー会議が既に動いているか
- **なぜ今**: 要件定義中の月次同期会議を Day-30 までに開始したい

### Q8. ★ 元請 SIer (1 社先) 経由のコミュニケーションルール
- **聞きたいこと**: BP 立場での顧客直接連携の境界 (どこまで直接 OK / どこから元請同席 / どこから事後報告)
- **なぜ今**: 初日から運用ルールを誤ると信頼を毀損する
- **想定回答例**: 「技術詳細は直接、商務・スコープは同席、緊急対応は事後報告」のような 3 分類

### Q9. ★ 顧客標準ツール環境 (進捗管理 / ドキュメント / コミュニケーション / 工数)
- **聞きたいこと**: Jira / ServiceNow / Confluence / SharePoint / Slack / Teams など。アカウントいつもらえるか
- **なぜ今**: 議事録 / 課題管理 / リスクレジスタ をどこに置くかが Day-1 で決まらないと運用が散らかる

### Q10. ★ 端末・アクセス権・VPN/閉域網の最初の段取り
- **聞きたいこと**: (a) 顧客貸与端末払い出しタイミング (b) VPN / VDI / 専用回線の利用方式 (c) 顧客環境ログイン (Identity Center / SSO) 開始時期 (d) 初週の出社可否・必要性・出社頻度 (e) アクセス権限申請の窓口・リードタイム (f) 個人 PC / 個人 SaaS 利用可否のルール
- **なぜ今**: 環境がないと業務が止まる。リードタイムが長ければスケジュール影響あり。BP/SES 立場で VPN 配布が遅れるケースを想定

### Q10-bis. ★ 行内独自規程 (RG-*) の受領窓口と一覧
- **聞きたいこと**: (a) 情報セキュリティ基本規程・技術基準 (b) システム監査規程 (c) クラウド利用ガイドライン (d) 個人情報保護規程 (e) 変更管理規程 (f) 業務継続・委託管理規程 のそれぞれの所管部署と受領窓口・受領期限
- **なぜ今**: FISC 第 11 版とは別に行内独自統制が存在するのが大手金融機関の常。要件定義中の受領遅延は基本設計の手戻りに直結。`業務用/80_規制対応/80-4_会社独自要件マッピング.md` の受領管理表を埋めるための情報

## 2. Should 質問 (◯、時間あれば、5 問、目安 8-10 分)

### Q11. ◯ 工程スケジュールの Exit Criteria 顧客合意状況
- **聞きたいこと**: 各フェーズ (要件定義〜総合テスト) の Exit 判定基準は顧客と既に握っているか、それともこれから握るか
- **なぜ**: 既に握っているなら逆算精度上がる。これからなら早期に提案する

### Q12. ◯ 業務 KPI (グループ顧客化促進 / グループ外損失利益低減) の数値定義
- **聞きたいこと**: 本システムの成功指標 (顧客化率 / クーポン利用率 / 金利優遇件数 等) の **数値定義と測定方法**
- **なぜ**: 非機能要件 (性能 / 拡張性) の目標値根拠になる

### Q13. ◯ CI/CD ツールの想定 (確定済み / PF 待ち)
- **聞きたいこと**: GitLab / Jenkins / CodePipeline / GitHub Actions のどれを想定しているか、いつ確定するか
- **なぜ**: 構築フェーズ着手前に決めたい (要件定義中の暫定先行のため)

### Q14. ◯ Cutover 後の運用保守体制と Hyper Care 想定
- **聞きたいこと**: Cutover 後 (2028/3 以降) の運用引継ぎ先と Hyper Care 期間。本案件で運用要件定義のみか、運用も継続担当する可能性があるか
- **なぜ**: 契約延長の見通しと、運用設計の深さに直結する

### Q15. ◯ 補強要員調達ルートと裁量
- **聞きたいこと**: 自分から要請する場合のルート (元請 営業 → 自社 / 別 BP) と、現実的なリードタイム
- **なぜ**: 構築 + 結合フェーズ重複期 (2027/5-11) のピーク要員を 2 ヶ月前から動かす必要がある

## 3. 今日は **聞かない** 方が良い項目 (後続で個別ヒアリング)

これらは「個別ヒアリングシート」(`業務用/10_要件定義/10-4_ヒアリングシート.md`) でじっくり聞く。初回業務説明で聞くと粒度過剰で時間を浪費する。

- ❌ 機能要件の詳細 (キャンペーン定義の属性、利用条件、通知チャネル等)
- ❌ 非機能要件の数値 (P95 レイテンシ、スループット、コスト上限)
- ❌ 個別 AWS サービスの選定理由 (ECS vs EKS、PostgreSQL vs MySQL 等)
- ❌ パラメータレベルの確認 (Aurora インスタンスクラス、Subnet CIDR 等)
- ❌ FISC 全項目の対応状況 (個別マッピングは別途レビュー会議で)
- ❌ 監査エビデンスの個別取得方法
- ❌ ペネトレーションテストの委託先選定

## 5. 質疑タイムでの言い回し例

質問は **「批判ではなく自分の動作のため」** という言い回しに統一する。

| ✗ NG (詰問調) | ◯ OK (協働調) |
|---|---|
| 「PoC はいつ終わるんですか?」 | 「PoC のスケジュール感がわかると、私の方で先行できるタスクの仕分けがしやすくなるのですが、現時点の見込みを教えていただけますか?」 |
| 「監査部門は誰が責任者?」 | 「FISC 対応マッピングを早めに整備したいので、監査部門の主担当の方と月次でレビューさせていただきたいのですが、どなたとお話しすればよいでしょうか?」 |
| 「ガイドラインがないと動けません」 | 「ガイドライン受領前に先行可能な領域 (業務要件 / 非機能要件項目体系 / FISC 第 11 版マッピング Draft 等) を進めていきたいので、その方向性で合意いただけますでしょうか?」 |
