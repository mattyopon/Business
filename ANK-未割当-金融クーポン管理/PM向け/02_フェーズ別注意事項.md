# PM-02. フェーズ別注意事項 (Yutaro 専用)

**目的**: 要件定義〜総合テストの各工程で **必ず陥る罠** と **回避策** を予め書き出す。経験上の「あー、これね」をすべて言語化する。

---

## 1. 要件定義 (2026/4-12) の注意事項

### 1.1 親システム / PF 側の「待ち」を案件停止の言い訳にしない

**罠**: 「PF 側ガイドライン待ちで進められません」「親システム I/F 待ちで…」を月次報告に書き続ける。3 ヶ月後に「何も進んでない」と顧客に怒られる。

**対策**:
- 毎週月曜の朝、**待ち項目** と **先行できる項目** を仕分けて Backlog 化
- 待ち項目には Owner と「待っている相手」と「次回連絡日」を必ず明記
- 先行項目を 80% の時間で進める。待ち項目は催促のみ
- 月次報告には「待ち項目 N 件」「先行進捗 M%」と必ず併記

### 1.2 非機能要件を「あとで」と先送りしない

**罠**: 機能要件で盛り上がり、非機能 (可用性 / 性能 / セキュリティ / バックアップ / 拡張性 / 運用性 / コスト) を要件定義 Exit 直前にまとめようとする。すると Aurora の RTO/RPO や ECS の Auto Scaling 閾値が不明のまま基本設計に突入し、手戻り。

**対策**:
- 要件定義 Day-7 までに非機能要件項目体系 (NFR-XX-NNN 形式) を顧客に提示・合意
- 月次で 1 領域ずつ深堀 (7 月: 可用性 / 8 月: 性能 / 9 月: セキュリティ / 10 月: バックアップ・拡張性 / 11 月: 運用・コスト)
- 各領域に必ず **目標値 (数値)** と **測定方法** をセット

### 1.3 FISC 第 11 版を「あとで」と先送りしない

**罠**: 「規制対応は基本設計でやればいい」と思い込み、要件定義中に FISC 対応マッピングを始めない。基本設計開始時にいきなり 200 項目以上の対応を求められ、手戻りが発生する。

**対策**:
- 要件定義 Day-30 までに **AWS FISC リファレンス第 2 版 (2024/8 公開)** をベースに全項目マッピング Draft 作成
- 第 11 版の項目は「クラウドサービス固有で対応すべき事項」が新設されているため、必ず最新版 (2023/3 公開) を参照
- 顧客監査部門と月次で進捗共有 (突然のレビュー要求を避ける)
- 出典: https://aws.amazon.com/jp/blogs/news/financereferencearchitecture-fisc11-update/

### 1.4 「全店名寄せ」「特別金利」「グループ顧客」の用語定義を曖昧にしない

**罠**: 顧客 / 親システム / PF 側で同じ言葉が違う意味で使われている。要件定義で気付かず基本設計に進むと、I/F 仕様で衝突する。

**対策**:
- 要件定義 Day-3 で「用語定義書」(別文書) を起票
- 親システム / PF 側 / 顧客部門それぞれが使う略称・正式名称を併記
- 設計レビューで「この用語の出典は?」を必ず確認

### 1.5 「PoC 中だから後で」と PF 側の限界を見落とす

**罠**: PF 側 PoC が「動いてる」と聞いて安心する。実は本システムの利用形態 (例: 高頻度の同時クーポン発行) がカバーされていない。

**対策**:
- PoC のスコープ (検証対象サービス / 規模 / 想定負荷) を必ず取得
- 本システムの予測ピーク (例: キャンペーン開始時の同時アクセス数) と比較
- ギャップがあれば「PoC 拡張」or 「本システムでの独自検証」を Day-30 までに合意

## 2. 基本設計 (2027/1-4) の注意事項

### 2.1 設計者の数を 2 名以上にする (NW / アプリで分割)

**罠**: SA 1 名で全領域 (NW / アプリ / データ / セキュリティ / 運用) を書こうとして 4 ヶ月で破綻

**対策**:
- 2027/1 開始時に SA を NW・データ側 1 名、アプリ側 1 名でアサイン
- レビュー責任は PM (自分) が一手に引き受ける
- 4 月 Exit 1 ヶ月前 (3 月末) には全文書 v0.9 が揃っている状態にする

### 2.2 ADR (Architecture Decision Record) を必ず書く

**罠**: 「なぜ ECS Fargate を選んだか」「なぜ Aurora PostgreSQL なのか (MySQL ではなく)」「なぜ CodePipeline ではなく GitLab CI か」を口頭合意で済ませる。**6 ヶ月後に誰も覚えていない**。Codex / 監査で「根拠は?」と詰められる。

**対策**:
- 主要設計判断は ADR (Markdown 1 件 1 ファイル) を必ず作成
- 構成: Context / Decision / Consequences / Alternatives
- 5 件以上は確実に出る (コンピュート / DB / NW / IaC / CI/CD)
- 詳細は `業務用/20_基本設計/20-1_システム方式設計書テンプレ.md` の付録 ADR 参照

### 2.3 詳細設計と並走するなら、責任分界を明確に

**罠**: 「基本設計と詳細設計を並走」と言われ、何を基本に書き何を詳細に書くか曖昧になる。基本設計レビューで「これは詳細では?」が頻発し、手戻り。

**対策**:
- 基本設計: 「**何を作るか** + **方式**」 (機能一覧、データモデル概要、NW 構成図、セキュリティ方針)
- 詳細設計: 「**どう作るか** + **パラメータ**」 (個別機能の処理フロー、テーブル定義、Subnet/SG/IAM 個別パラメータ)
- 並走スタート時 (2 月) に責任分界マトリクスを書面化

### 2.4 NW 設計は **PF 側方針確定後** に着手

**罠**: 自分側で先行して VPC / Subnet 設計を進めたら、PF 側の TGW 接続方針が決まって全部やり直し

**対策**:
- NW は **PF 側ガイドライン v1.0 受領後** に着手 (要件定義 Exit 後)
- それまでは「ローカル単体検証用」の暫定 VPC を MUT で構築 (本番設計とは分離)

## 3. 詳細設計 (2027/2-5) の注意事項

### 3.1 パラメータ確定の責任分界

**罠**: 「パラメータシートを書く」と言いつつ、何のパラメータを誰が決めるかが曖昧。Terraform `apply` 直前に「これ未定だった」が大量発覚。

**対策**:
- リソース別パラメータシート (VPC / ECS / Aurora / S3 / IAM / Route53 / CloudWatch / EFS / Change Calendar) を 4 月末までに **すべての項目を起票**
- 各項目に Owner (顧客 / PF 側 / 自チーム) と確定期限を明記
- 詳細設計 Exit (5 月末) は全項目確定が条件
- テンプレ: `業務用/30_詳細設計/パラメータシート/`

### 3.2 ハルシネーションを許さない

**罠**: 「AWS のこの機能はこう動くと思います」を確認せずに設計書に書く。Codex レビューで全部指摘されて手戻り。

**対策**:
- 仕様引用は必ず AWS 公式 (docs.aws.amazon.com) の URL とバージョン明記
- 不確実な記述は「未確認 (要 PoC / 要 AWS Support 確認)」と明示
- 設計書末尾に「出典」セクション必須

### 3.3 Terraform バージョン / Provider バージョン固定

**罠**: 設計時の AWS Provider バージョンと構築時のバージョンが違って動かない

**対策**:
- 詳細設計 Day-1 で `required_providers` バージョンを固定 (例: `hashicorp/aws ~> 5.100`)
- バージョン更新は必ず PR レビュー経由

## 4. 構築 (MUT / LT / ST、2027/2-9) の注意事項

### 4.1 MUT は「動けばいい」、LT は「整える」、ST は「本番相当」

**罠**: 全環境で同じ品質を目指して MUT で時間を浪費

**対策**:
- MUT: 単体動作確認のみ。Auto Scaling 最小、Multi-AZ なし、暗号化最小
- LT: マスタテストを通す環境。Multi-AZ あり、暗号化あり、本番に近いが規模小
- ST: 本番相当。性能試験・セキュリティ試験対応
- 環境別 Terraform variables で差分管理

### 4.2 `terraform apply` の人手承認ゲート

**罠**: CI/CD で自動 apply にして本番事故

**対策**:
- ST 以降は必ず人手承認 (GitHub Environment Required reviewer or CodePipeline Manual Approval)
- 承認者は PM (自分) + IaC リード の 2 名以上
- 詳細は `業務用/40_構築/40-3_CI-CDパイプライン定義.md`

### 4.3 Change Calendar 凍結期間を初期に設計

**罠**: 構築後半で「年末年始の凍結期間どうします?」と聞かれて慌てる

**対策**:
- 詳細設計時に AWS Systems Manager Change Calendar の OPEN/CLOSED 状態管理設計
- 凍結期間例: 年末年始 (12/29-1/4)、月末月初 (顧客指定)、本番障害時の自動 CLOSED
- 出典: https://docs.aws.amazon.com/ja_jp/systems-manager/latest/userguide/systems-manager-change-calendar.html
- 詳細: `業務用/40_構築/40-4_Change_Calendar設計.md`

### 4.4 Aurora の暗号化キーは **構築前** に決める

**罠**: 構築開始後に「KMS CMK 使うべきだった」と気付き、再作成が必要に

**対策**:
- Aurora は **作成時にしか暗号化指定できない** → 設計時に KMS CMK 使用を確定
- KMS Key は別アカウントなら共有が必要 (cross-account snapshot 制約)
- 出典: https://aws.amazon.com/blogs/database/encrypting-amazon-aurora-using-aws-kms-and-your-own-cmk/

## 5. 運用機能開発 (2027/6-10) の注意事項

### 5.1 監視は「アラートが出る」では不十分、「対応できる」まで設計

**罠**: CloudWatch Alarm を設定して終わり。実際の発火時に「で、どうする?」が決まっておらず夜間呼び出しで運用崩壊

**対策**:
- 各アラートに対応 Runbook (Confluence 1 ページ) を必ずセット
- アラート → 通知先 → 一次対応者 → エスカレーション先 → 復旧手順 を必ず明記
- 詳細: `業務用/60_運用/60-2_監視運用設計書.md`

### 5.2 バッチは「正常完了」だけでなく「異常検知」「再実行」も設計

**罠**: バッチ正常完了のみ監視で、長時間 hang・部分成功・データ不整合に気付かない

**対策**:
- 完了通知 / タイムアウト通知 / データ件数チェック / 再実行可否 (冪等性) を必ず設計
- 親システムからの取り込みバッチは特に重要 (前日分が来ない → クーポン発行できない)

## 6. 結合試験 (2027/10-11、12-1) の注意事項

### 6.1 親システム連携試験は **早期** に計画

**罠**: 結合試験開始時に親システム側のテスト環境スケジュール調整が始まり、2 週間の遅延

**対策**:
- 2027/6 (運用機能開発開始時) には親システム側責任者と試験計画を握る
- 親システム側のテスト窓口を Day-1 で特定 (キックオフ時に PM 同士で握る)

### 6.2 性能試験は **負荷ツール選定** から逆算

**罠**: ST 構築完了後に「JMeter? k6? Locust?」を議論開始、結局 1 ヶ月遅延

**対策**:
- 基本設計時に性能試験計画 Draft を作成 (`業務用/50_テスト/50-3_性能試験計画.md`)
- 負荷ツール / シナリオ / 目標 / 判定基準を早期確定

### 6.3 本番構築・結合は **本番リハーサル必須**

**罠**: 本番初 apply で実行順序ミスで TGW 接続が外れる

**対策**:
- 本番 apply 前に ST 環境で「apply 順序リハーサル」 (Terraform plan の段階別実行 / 依存確認)
- 本番リハーサル: 12 月中旬に最低 1 回、1 月初旬に最終リハーサル

## 7. 総合テスト (2028/1-3) の注意事項

### 7.1 切り戻しは **絶対に必要**

**罠**: 「Cutover 前提で切り戻しは考えない」と進め、本番障害で大事故

**対策**:
- 切り戻し手順書を必ず作成 (`業務用/70_移行/70-3_切り戻し手順書.md`)
- 総合テストで切り戻しシナリオを 1 回は通す
- Cutover 判定基準に「切り戻し可能であること」を必ず入れる

### 7.2 DR (Disaster Recovery) リハーサルを必ず実施

**罠**: 「Multi-AZ あるから大丈夫」で AZ 障害シナリオを試さない

**対策**:
- 総合テストで以下を最低 1 回ずつ実施:
  - AZ 障害 (Aurora Multi-AZ Failover)
  - リージョン障害 (DR サイト切替、もしあれば)
  - データ破損 (Point-in-Time Recovery、Aurora は 1-35 日保持)
- 出典: https://aws.amazon.com/solutions/guidance/disaster-recovery-using-amazon-aurora/

### 7.3 監査エビデンスを **総合テスト中に取得**

**罠**: 監査エビデンスを Cutover 後に取得しようとして、本番ログで監査人が NG

**対策**:
- FISC / 金融庁ガイドライン対応エビデンスを総合テスト中に取得・保管
- 取得対象: CloudTrail / Config / GuardDuty Finding / KMS 利用ログ / IAM 利用ログ
- 詳細: `業務用/80_規制対応/80-3_監査エビデンス一覧.md`

## 7-bis. リフトアンドシフト案件特有の注意事項 (本案件の最重要)

### 7-bis.1 既存システム調査を要件定義に必ず組み込む

**罠**: 「リフトだから既存をそのまま動かせばいい」と楽観し、既存システム調査をスキップ。MUT 環境で初回起動失敗 + 同等性検証で大量の差異検出。

**対策**:
- 要件定義 Day-7 までに既存システム保守担当者と接続 (週次同期)
- 要件定義 Day-30 までに既存システムの **ソースコード + 設定値 + 起動手順 + データ仕様** をすべて入手
- 環境依存性 (オンプレ固有設定 / 内部 IP 直書 / NW ファイルシステム前提) を全件棚卸
- 移行設計を基本設計内に組込 (詳細設計に後送り NG)

### 7-bis.2 「変えない判断」を恐れない

**罠**: 「クラウドに乗せるなら、ついでにマネージドサービスに置き換えよう」と判断が膨らみ、スコープクリープ + 同等性検証 NG。

**対策**:
- リフトアンドシフトの目的は「既存をクラウドに乗せる」 (リアーキテクチャは別案件)
- 機能改善・最適化は Cutover 後 6 ヶ月以降に別フェーズで計画
- 改善案が浮かんだら Backlog 化 (今は実行しない)

### 7-bis.3 同等性検証を「動けばいい」で済まさない

**罠**: 「クラウドで動いた! ヨシ!」で済ませ、性能・整合性で既存実績との差を見落とす。

**対策**:
- レスポンス時間 / スループット / エラー率 / バッチ完了時間を既存実績と数値で比較
- 既存環境と並行動作 (Shadow Traffic) を Day-30 までに合意可能か確認
- 性能試験 (ST 環境) で既存実績ベンチマークを目標値とする

### 7-bis.4 データ移行設計を後回しにしない

**罠**: 「データ移行は構築フェーズで考えればいい」と先送り、設計工程で前提条件が固まらず手戻り。

**対策**:
- 基本設計時にデータ移行設計を必ず組込 (`業務用/70_移行/70-1_本番移行計画書.md` § 4)
- 移行方式 (DB dump / API / バッチファイル) は要件定義中に既存保守側と合意
- 件数 + ハッシュ検証で整合性確認、リハーサルは LT/ST で 2 回以上

## 7-ter. 大手金融機関 初参画特有の注意事項

### 7-ter.1 「VPN/閉域網 + 顧客貸与端末」前提の作業計画

**罠**: 個人 PC で先行作業しようとして顧客環境にアクセスできない / 個人 GitHub に機密含めて push してしまう。

**対策**:
- 入館証 + 端末払い出しの **リードタイム (1-2 週間)** を考慮し、Day-1 の動きは「来客対応 + ヘルプデスクとの調整」が中心になる前提
- 個人 PC は **顧客環境に絶対繋がない**
- 詳細は `PM向け/10_金融機関案件初参画ガイド.md` § 2

### 7-ter.2 行内独自統制 (RG-*) を FISC と並列で追跡

**罠**: FISC 対応マッピング (80-1) だけ整備し、行内独自規程 (80-4) を後回し → 監査部門レビューで突然 NG。

**対策**:
- 要件定義 Day-7 から監査部門と月次会議
- `業務用/80_規制対応/80-4_会社独自要件マッピング.md` を Day-30 まで起票・受領追跡
- ギャップ分析は受領後 2 週間以内に提示

### 7-ter.3 「だいたい」「割と」「たぶん」を使わない

**罠**: 金融機関では曖昧表現は信用失墜要因。「だいたい 1 秒くらい」→「P95 で 980ms、P99 で 1.2 秒」のように数値で語る。

**対策**:
- 報告・回答は **数値で**
- 不明な数値は「未確認 (○月○日までに確認します)」と明示
- 議事録の文言も曖昧表現を排除

### 7-ter.4 報告は悪い報告ほど早く

**罠**: ネガティブ情報を隠そうとして報告が遅れる → 後で発覚した時の信用毀損は致命的。

**対策**:
- 悪い兆候は **24 時間以内** に元請 PL + 顧客主担当に第一報
- 第一報は「事実 + 影響範囲 + 対応案 + 確認したいこと」
- 詳細は後追いで OK

### 7-ter.5 稟議・承認のリードタイム逆算

**罠**: 「来週の CAB で承認取って...」で予定すると、稟議が長引いて2週間遅延。

**対策**:
- 稟議書フォーマット・承認階層を Day-7 までに把握
- 主要意思決定 (リソース申請・例外申請・体制変更) は **1 ヶ月前** から仕込み
- マスタープランに稟議リードタイムを含める

## 8. 全フェーズ共通の注意事項

### 8.1 「自分が忙しい」を理由にチーム放置しない

**罠**: PM 兼プレイヤーで自分が手作業に没頭し、チームメンバーが詰まっていることに気付かない → メンバーが離脱

**対策**:
- 週次 1on1 (15 分) を必ず実施
- 朝会で blocker を必ず聞く
- 「Slack の DM 確認」を 1 日 3 回 (始業 / 昼 / 終業前)

### 8.2 顧客との温度感を保つ

**罠**: 月次報告だけで顧客との関係が薄くなり、ある日突然「もっと細かく報告して」と怒られる

**対策**:
- 週次報告必須 (テンプレは `PM向け/05_週次PMルーチン.md`)
- 隔週で顧客責任者と非公式 30 分 (進捗だけでなく雑談含む)
- 主要マイルストーン前後で必ず面談

### 8.3 ハルシネーション禁止 (再掲)

**罠**: 「たぶんこう」を設計書に書く → Codex / 監査人で全部指摘される

**対策**:
- AWS / Terraform / FISC / 金融庁規制の引用は必ず公式 URL とバージョン明記
- 不確実な部分は「未確認」「PoC 結果待ち」と明示
- 設計書末尾に出典セクション必須

### 8.4 ドキュメント保管・命名規則を守る

**罠**: Confluence / SharePoint / S3 / GitHub にバラバラに置いて検索不能化

**対策**:
- 顧客標準ツール (おそらく Confluence) に **全成果物の Index** を維持
- 命名規則: `{文書 ID}_{文書名}_v{版}_{YYYYMMDD}.md` 等を Day-1 で合意
- 詳細は既存ANK資産 G3 (ナレッジ管理体系) を参考
