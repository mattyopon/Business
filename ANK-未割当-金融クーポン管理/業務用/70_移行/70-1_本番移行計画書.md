## 4. データ移行 (該当する場合)

### 4.1 移行データ
- 顧客 ID (親システムから取込、初回フルロード)
- マスタデータ (キャンペーン / 商品 / 利用条件)
- (既存システム由来データがあれば) 過去履歴

### 4.2 移行方式
- 親システム → S3 → ECS Batch → Aurora (バッチ取込)
- ファイル形式 / 件数 / 整合性 確認

### 4.3 検証
- 件数一致 (件数比較)
- サンプル整合性確認 (100 件)
- マスタデータの整合性 (顧客 / マスタとの関連性)
- データ品質チェック (必須項目 / 型 / 重複)

---

## 5. 切替方法

### 5.1 DNS 切替
- Route 53 Weighted Routing (段階切替) or Failover
- TTL を事前に短縮 (60 秒) → 切替後に戻す

### 5.2 既存システム停止 (該当時)
- 既存系の停止手順 (運用部門責任)
- 停止確認後に本番アクセス再開

## 6. Cutover 判定基準

### 6.1 Go 判定 (全項目クリア必須)
- [ ] 総合テスト全シナリオ PASS
- [ ] 重要不具合 0 件
- [ ] 性能 SLO 達成
- [ ] DR リハーサル PASS
- [ ] 切り戻し手順検証 PASS
- [ ] FISC 第 11 版エビデンス取得済
- [ ] 監査部門承認
- [ ] Hyper Care 体制確定
- [ ] Cutover リハーサル #2 PASS
- [ ] 凍結期間 (CAB 経由) 確保済

### 6.2 No-Go 判定 (1 項目でも該当)
- 重要不具合の残存
- 性能 SLO 未達
- 切り戻し手順未検証
- 主要関係者の不承認

### 6.3 判定会議
- 開催: Cutover -1 週間
- 参加: PM + 顧客責任者 + 顧客 IT 統括 + 元請 PL + 監査部門 + CIO
- 詳細は [PM向け/06_会議体運営テンプレ](../../PM向け/06_会議体運営テンプレ.md) § 3.6

## 7. リスク管理

### 7.1 Cutover 当日リスク

| リスク | 影響 | 対策 |
|---|---|---|
| データ移行件数不一致 | 高 | 件数比較・整合性確認・サンプル監視 |
| 親システム連携障害 | 高 | 親システム側待機 + 即時連絡 |
| PF / 勘定系連携障害 | 高 | PF 側待機 + 即時連絡 |
| 性能劣化 | 中 | 監視 + 一時的なアクセス制限 (WAF) |
| 想定外バグ | 高 | 切り戻し手順発動 |
| 担当者の体調不良 | 中 | バックアップ要員確保 |

### 7.2 切り戻し基準
- Cutover 開始後 X 時間以内に重要不具合発生 → 切り戻し検討
- 詳細は [70-3_切り戻し手順書](70-3_切り戻し手順書.md)

## 9. Hyper Care 期間 (Cutover 後 90 日)

### 9.1 体制
- 案件チームが Tier 2-3 を維持
- 顧客運用部門が Tier 1
- 週次振り返り会議

### 9.2 監視強化
- 全メトリクス Anomaly Detection ON
- 24x365 オンコール (要件次第)
- 日次顧客報告 (Hyper Care 前半 30 日)

### 9.3 終了判定
- Hyper Care 期間中の重大障害 0 件 (or 全て Postmortem 済)
- Runbook 全件完成
- 運用部門が Tier 1 業務を独立実施できる
