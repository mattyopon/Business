# リスクレジスタ - 金融機関 AWS クラウド共通基盤案件

本案件における想定リスクおよび緩和策の一覧である。参画前および参画初期に各リスクの該当状況を確認し、必要に応じて緩和策を検討する。

---

## 凡例

- **影響度（Impact）**: 高／中／低（プロジェクト全体または担当業務に対する影響）
- **発生確率（Likelihood）**: 高／中／低
- **総合スコア**: 影響度 × 発生確率の組合せから、対応優先度を判定

---

## R-001：要件定義期間の不足

| 項目 | 内容 |
|------|------|
| カテゴリ | スケジュール |
| 影響度 | 高 |
| 発生確率 | 高 |
| 概要 | 共通基盤の要件定義に充てられる期間が短く、要件の確定度合いが低いまま後工程に着手する可能性がある。 |
| 兆候 | 要件定義中間成果物が未整備／未確定事項リストの件数が多い／要件定義と基本設計が同時並行で進行している |
| 影響 | 後工程での手戻り、設計品質の低下、本番稼働遅延 |
| 緩和策 | (1) 参画前に未確定事項リストの開示を依頼 (2) 要件定義の Exit Criteria を文書化 (3) 段階的な要件凍結（フェーズドアプローチ）の提案 |
| モニタリング | 週次の未確定事項クローズ件数を可視化 |

## R-002：要件定義と設計の並行実施による手戻り

| 項目 | 内容 |
|------|------|
| カテゴリ | スケジュール／品質 |
| 影響度 | 高 |
| 発生確率 | 中 |
| 概要 | 要件定義と基本設計の期間が重複しており、要件未確定のまま設計を進めることで設計の再実施が発生する可能性がある。 |
| 影響 | 設計工数の増加、整合性確保のための追加作業 |
| 緩和策 | (1) 設計開始の前提条件を明示 (2) 要件変更時の設計影響範囲を ADR として記録 (3) アジャイル的な反復設計の導入提案 |

## R-003：規制要件（FISC等）への対応漏れ

| 項目 | 内容 |
|------|------|
| カテゴリ | 規制対応／品質 |
| 影響度 | 高 |
| 発生確率 | 中 |
| 概要 | FISC 安全対策基準、金融庁ガイドラインなど金融特有の規制要件が要件定義段階で十分に取り込まれず、設計工程以降での追加対応が必要となる可能性がある。 |
| 影響 | 設計変更、構築工程での追加コスト、リリース遅延 |
| 緩和策 | (1) 監査部門・セキュリティ部門との早期コミュニケーション (2) FISC 安全対策基準と AWS サービスの対応マッピングを早期に作成 (3) AWS の FISC 対応リファレンス・FSI Lens for FISC の参照 |

## R-004：スコープ拡大による負荷集中

| 項目 | 内容 |
|------|------|
| カテゴリ | スコープ／体制 |
| 影響度 | 高 |
| 発生確率 | 中 |
| 概要 | 「マルチアカウント／ネットワーク／IAM／セキュリティ／IaC／CI/CD／運用」と広範な領域が要件として求められており、特定の担当者に対応領域が集中する可能性がある。 |
| 影響 | 担当者の稼働超過、品質低下、納期遅延 |
| 緩和策 | (1) 契約段階で担当領域を明確化 (2) 領域別の専門メンバー配置を提案 (3) RACI 表の整備と関係者承認 |

## R-005：意思決定権者の不明確化

| 項目 | 内容 |
|------|------|
| カテゴリ | ガバナンス |
| 影響度 | 中 |
| 発生確率 | 中 |
| 概要 | クライアント側・元請 SIer・AWS Professional Services 等、複数の関係者が関与することで、意思決定権限の所在が不明確になる可能性がある。 |
| 影響 | 設計方針の決定遅延、関係者間での認識齟齬 |
| 緩和策 | (1) ステークホルダー分析の実施 (2) RACI 表の作成と合意 (3) 設計判断記録（ADR）による意思決定プロセスの可視化 |

## R-006：既存ベンダー・既存資産との整合

| 項目 | 内容 |
|------|------|
| カテゴリ | 技術／調整 |
| 影響度 | 中 |
| 発生確率 | 高 |
| 概要 | 既存のオンプレミスインフラ、メインフレーム、既存ベンダーが整備した CloudFormation 等の資産との整合が必要となる可能性がある。 |
| 影響 | 設計の制約増加、技術選定の自由度低下 |
| 緩和策 | (1) 既存資産の棚卸し依頼 (2) 既存ベンダーとの定例コミュニケーション枠の確保 (3) 移行方針（共存／置換）の早期明確化 |

## R-007：IaC ツール選定に関する宗教的対立

| 項目 | 内容 |
|------|------|
| カテゴリ | 技術選定 |
| 影響度 | 中 |
| 発生確率 | 中 |
| 概要 | Terraform、CDK、CloudFormation など IaC ツールの選定において、関係者間で強い選好の差が生じる可能性がある。LZA は内部で CloudFormation を採用しているため、上位レイヤーで Terraform を併用する場合の方針整理が必要となる。 |
| 影響 | 設計フェーズでの議論長期化、合意形成の遅延 |
| 緩和策 | (1) 選定基準（評価軸）の事前合意 (2) ADR による選定根拠の文書化 (3) 既存スキルセット・運用継続性を考慮した加点評価 |

## R-008：監査ログ保管要件と運用コストのバランス

| 項目 | 内容 |
|------|------|
| カテゴリ | 規制対応／コスト |
| 影響度 | 中 |
| 発生確率 | 中 |
| 概要 | 金融機関では監査ログの長期保管（7年〜10年）が求められる場合があり、S3 Glacier 等のコスト最適化と、検索性・可用性のバランスが論点となる。 |
| 影響 | 運用コストの肥大化、検索パフォーマンスの低下 |
| 緩和策 | (1) ログ種別ごとの保管要件の整理 (2) S3 ライフサイクル＋Object Lock 等の組合せ設計 (3) Athena／OpenSearch 等の検索基盤との分離設計 |

## R-009：Direct Connect 物理設計の専門外領域

| 項目 | 内容 |
|------|------|
| カテゴリ | 技術／スコープ |
| 影響度 | 中 |
| 発生確率 | 低〜中 |
| 概要 | Direct Connect の物理回線設計・キャリア選定など、ネットワーク物理面の専門領域が含まれる場合、対応が困難な可能性がある。 |
| 影響 | 設計品質低下、外部ベンダーへの依存 |
| 緩和策 | (1) 物理設計はネットワークベンダーへの委託を前提化 (2) 論理設計と物理設計のインタフェース定義の明確化 |

## R-010：出社頻度に関する取り決め

| 項目 | 内容 |
|------|------|
| カテゴリ | 働き方／契約 |
| 影響度 | 低〜中 |
| 発生確率 | 中 |
| 概要 | 案件概要では「週3〜4日」とされているが、要件定義フェーズでは現場常駐傾向が強く、契約上の取り決めと実態に乖離が生じる可能性がある。 |
| 影響 | 通勤負荷、稼働時間の実質増加 |
| 緩和策 | (1) 契約上の出社頻度の明文化 (2) 会議体のオンライン化提案 (3) フェーズごとの出社頻度見直し条件の合意 |
