# 参画初週確認チェックリスト - 金融機関 AWS クラウド共通基盤案件

参画後 1〜2 週間で確認することが望ましい事項を整理したチェックリストである。要件定義および基本設計の前提条件を早期に把握することを目的とする。

設問は **AWS 公式ドキュメント** および **AWS Well-Architected Framework (Financial Services Industry Lens 含む)** **AWS 金融リファレンスアーキテクチャ日本版** などの一次資料に基づいて構成している。

---

## A. 非機能要件（IPA 非機能要求グレード ベース）

### A-1. 非機能要件整理の前提
- [ ] IPA 非機能要求グレードを要件定義の出発点として使用しているか、または独自テンプレートを使用しているか。
- [ ] 社会的影響度モデルは「大」「中」「小」のいずれをベースラインとしているか。
- [ ] グレード表のレベル（0-5）において重要項目として明示済みの行はいくつあるか。

### A-2. 非機能要件の各カテゴリ
- [ ] 可用性: 運用時間／稼働率／目標復旧時間（RTO）はサービス別に確定済みか。
- [ ] 性能・拡張性: レスポンス順守率／同時アクセス数／3年程度の拡張係数は仮置きか確定か。
- [ ] 運用・保守性: バックアップ取得頻度／データ復旧範囲／監視間隔は決定済みか。
- [ ] 移行性: 移行期間／移行データ量／リハーサル回数の前提は何か。
- [ ] セキュリティ: 暗号化方式（保存時／通信時）／診断頻度／インシデント対応体制は記載済みか。
- [ ] システム環境: ラック設置／耐震／電源条件はクラウド利用前提で書き換え済みか。

### A-3. 補完および変更管理
- [ ] グレード表にない項目（AI／生成AIガバナンス、SBOM 等）を補完する別チェックリストは存在するか。
- [ ] 重要項目以外のレベル決定は誰が裁定するか。
- [ ] 非機能要件の変更管理プロセス（承認者、凍結条件）は決定済みか。
- [ ] 共通基盤と個別アプリで適用レベルが分かれる場合の継承ルールは定義済みか。

## B. AWS Well-Architected Framework / FSI Lens

### B-1. WAR（Well-Architected Review）の実施状況
- [ ] WAR は実施済みか。実施時期、実施者、使用した Lens を確認する。
- [ ] 6 Pillar 別の評価スコアおよび High Risk Issue (HRI) は記録されているか。
- [ ] AWS Financial Services Industry Lens は AWS Well-Architected Tool にロード済みか、また FSI Lens for FISC（AWS 金融リファレンスアーキテクチャ日本版 GitHub 公開）は取得済みかつ評価に活用できているか。

### B-2. Reliability / DR
- [ ] RTO／RPO はシステム別／サービス階層別に決定済みか。
- [ ] 選択した DR 戦略は Backup & Restore／Pilot Light／Warm Standby／Multi-Region Active-Active のいずれか。
- [ ] DR 戦略の選択根拠（コストと RTO のトレードオフ）は文書化されているか。
- [ ] フェイルオーバーは自動か手動か。誤検知時のリスクをどのように許容するか。
- [ ] Control Plane 依存を排除した手動フェイルオーバーの仕組み（Amazon Application Recovery Controller 等）の採用方針。
- [ ] DR テスト（障害注入、リージョン疎結合）の頻度および実施記録の有無。
- [ ] Failback 計画（本番リージョン復旧後の戻し手順）は Playbook 化されているか。

### B-3. その他 Pillar
- [ ] Security Pillar の MFA／KMS／IAM 設計は FSI Lens の推奨に準拠しているか。
- [ ] Cost Optimization Pillar のタグ戦略／Savings Plans／RI／コスト配分は要件化されているか。
- [ ] Sustainability Pillar の指標（リソース最適化、Graviton 採用等）は要件に含まれているか。
- [ ] Operational Excellence の Runbook／Playbook は IaC 化を前提に設計されているか。

## D. マルチアカウントおよびガードレール

### D-1. アカウント発行

- [ ] Account Factory for Terraform (AFT) ／ ServiceNow Connector ／ AWS Service Catalog ／ Backstage 等のいずれを採用予定か。

### D-2. ガードレール（Preventive／Detective／Proactive）
- [ ] Preventive (SCP) の現行ルール一覧（Region Deny／Root API 制限／VPC 共有制限など）は文書化されているか。
- [ ] SCP の例外申請プロセス（承認者、期間限定か恒常か）は決定済みか。
- [ ] Detective (Config Rule + Conformance Pack) はどの Pack を採用しているか（FISC／CIS／FSBP 等）。
- [ ] Config Rule の自動修復（SSM Automation）と手動修復の分け方ルールは決定済みか。
- [ ] Proactive コントロール（CloudFormation Hooks ベースの事前評価）の採用方針。
- [ ] アプリケーションコードの静的解析ツール（Amazon CodeGuru Security 等）の採用方針（Proactive コントロールとは別系統の論点として整理）。
- [ ] AWS Security Hub／GuardDuty／Inspector／Macie の有効化アカウント範囲。
- [ ] Security Hub の集約先（Delegated Administrator）は Audit アカウントか。
- [ ] ガードレール変更のテストは PolicyStaging OU で先行検証しているか。
- [ ] ガードレール例外の有効期限を自動失効させる仕組み（期限切れ通知）はあるか。
- [ ] AWS の新サービスをリリース直後に検証する経路（Sandbox OU の独立 SCP）の有無。
