## 1. プロジェクト全体に関する質問

### Q1-1. クラウド共通基盤を構築する目的をどのように整理するか。
A. 一般的にクラウド共通基盤の構築目的は、以下の観点で整理される。

1. **ガバナンスの一元化**: アカウント単位で分散していたセキュリティ・コスト・運用の統制を一元化する。
2. **スピード**: アカウント発行、ネットワーク接続、セキュリティベースラインの適用を自動化することで、利用部門の AWS 利用着手までのリードタイムを短縮する。
3. **コスト最適化**: タグ戦略および AWS Cost Categories による配賦設計、Savings Plans／RI の集中購入による単価最適化を実現する。
4. **規制対応**: FISC 安全対策基準、金融庁ガイドラインなどの規制要件を共通基盤側で吸収し、利用システム側の負担を軽減する。
5. **人材リソース**: 個別システムごとに必要だった AWS スキルを共通基盤チームに集約することで、組織全体の人材効率を高める。

### Q1-2. 共通基盤と個別システムの責任分界はどのように整理するか。
A. 一般的に「共通基盤側」が責任を持つ範囲と、「利用システム側」が責任を持つ範囲を明確に定義する。

- **共通基盤側**: アカウント発行、ネットワーク基盤、IAM ベースライン、セキュリティサービス（GuardDuty／Security Hub／Config）、監査ログ集約、ガードレール、共通的なシークレット管理基盤、共通的な監視基盤
- **利用システム側**: 個別アプリケーションの実装、アプリケーション固有のリソース、利用システム単位の運用、利用システム単位のコスト管理

責任分界をマトリクス化して、共通基盤利用ガイドラインに記載することが望ましい。

### Q1-3. 共通基盤の要件定義で最も難しい点は何か。
A. 一般的に以下の点が難しいとされている。

1. **利用者像の多様性**: 利用部門のスキルセット、業務特性、運用体制が多様であり、共通基盤の「標準」をどこに置くかの合意形成が難しい。
2. **規制要件の解釈**: FISC 安全対策基準などの規制要件を AWS のサービスに具体的にマッピングする際、解釈の幅が生じる。
3. **既存資産との整合**: 既存のオンプレミス基盤、既存ベンダーが整備した CloudFormation 資産との整合が必要となる場合がある。
4. **スピードと統制のトレードオフ**: ガードレールを強化すると利用者の自由度が低下し、緩めると統制が効かない。

## 2. マルチアカウント設計に関する質問

### Q2-1. AWS Landing Zone Accelerator (LZA) と AWS Control Tower はどちらを採用すべきか。
A. 採用基準は以下のように整理できる。

- **AWS Control Tower**: マネージドな範囲が広く、運用負荷が低い。標準的なガードレール（必須／強推奨／選択）を採用する場合に適している。
- **AWS LZA**: 規制業界向けに最適化された構成テンプレートが提供されており、より柔軟なカスタマイズが可能。金融機関の独自要件が多い場合に適している。LZA Compliance Workbook（2026 年 3 月公開）により、複数のフレームワーク統合が容易になっている。
- **独自構築**: 既存資産が多くマネージドサービスに乗せ替えが困難な場合に検討されるが、運用負荷が大きい。

選定に際しては、規制要件、運用体制、既存資産、将来の拡張性を評価軸として比較するアプローチが一般的である。

### Q2-2. OU 設計はどのような構成を推奨するか。
A. AWS Control Tower の推奨 OU 構成は以下のとおり。

- **Security OU**（必須）: Log Archive アカウント、Audit アカウント
- **Sandbox OU**: 実験用アカウント
- **Infrastructure OU**: 共通ネットワーク、共有サービス
- **Workloads OU**: 本番／ステージング／開発アカウント
- **PolicyStaging OU**: ポリシー変更の事前検証用
- **Suspended OU**: 利用停止アカウント

金融機関では Workloads OU を事業部別／環境別に階層化し、SCP の継承を活用するパターンも一般的である。

### Q2-3. Account Factory for Terraform (AFT) と Service Catalog の使い分けは。
A. 一般的な使い分けは以下のとおり。

- **AFT**: アカウントの発行・運用を GitOps スタイルで管理する場合に採用。Terraform に習熟した運用チームを前提とする。
- **Service Catalog**: アカウント発行に加え、ユーザーが起動できるリソース（VPC テンプレート等）を承認済みカタログとして提供する場合に採用。
- **ServiceNow Service Management Connector**: 既存の ServiceNow 運用がある場合、アカウント申請ワークフローを ServiceNow 側で完結させることが可能。

## 3. ネットワーク設計に関する質問

### Q3-1. Transit Gateway と Cloud WAN のどちらを採用すべきか。
A. 採用基準は以下のように整理できる。

- **Transit Gateway**: 単一リージョン内、または限定的なマルチリージョンでの利用に適している。設定がシンプルで、既存の採用事例が多い。
- **Cloud WAN**: 複数リージョン、複数の地理拠点を統合管理する場合に適している。グローバルネットワーク管理が必要な場合に検討する。

金融機関では、東京リージョン中心の運用で開始し、将来的に大阪リージョン併用の DR 構成に拡張する場合は Transit Gateway で十分なケースが多い。

### Q3-2. 集中型 Egress と分散型はどちらが適切か。
A. 双方の特性を以下に整理する。

- **集中型 Egress**: AWS Network Firewall を共通の Network アカウントに配置し、全 VPC からの外向き通信を集約する。統制が効きやすく、監査対応が容易。一方で、スループットおよびコストの観点で大規模化時にボトルネックとなる可能性がある。
- **分散型**: 各 VPC で独立した Egress 制御を行う。スケーラビリティに優れるが、統制が分散する。

金融機関では一般的に集中型を採用し、特定の高スループット用途のみ分散型を併用するハイブリッドパターンが採用されることが多い。

### Q3-3. Direct Connect の冗長構成はどのように設計するか。
A. AWS が推奨する Direct Connect の冗長構成は以下のとおり。

1. **複数の DX Location**: 異なる物理ロケーションから 2 本以上の専用線を引く。
2. **複数のキャリア**: 異なる通信事業者を経由することで、キャリア障害に対するレジリエンスを確保する。
3. **VPN バックアップ**: Direct Connect 障害時に AWS Site-to-Site VPN へのフェイルオーバーを構成する。

金融機関ではミッションクリティカルなシステムについて、上記の組合せを採用するケースが多い。

## 4. IAM・アイデンティティに関する質問

### Q4-1. IAM Identity Center と既存 AD/Entra ID の連携はどのように設計するか。
A. 一般的な連携パターンは以下のとおり。

1. **Entra ID（旧 Azure AD）連携**: SAML 2.0 または SCIM を用いてユーザー／グループを同期する。
2. **オンプレ AD 連携**: AD Connector または AD FS を経由して認証連携する。
3. **属性マッピング**: AD／Entra ID のグループを Permission Set にマッピングする設計を事前に整理する。

属性マッピングの粒度（部署単位／プロジェクト単位／職位単位）を事前に決定することが、後工程での再設計を防ぐ鍵となる。

### Q4-2. Permission Set はどのような粒度で設計すべきか。
A. 一般的な設計指針は以下のとおり。

- **ジョブ機能別**: 管理者、開発者、運用者、監査者、読み取り専用 等
- **環境別**: 本番／ステージング／開発で異なる権限
- **AWS マネージドポリシーを基盤とし、不足分をカスタマーマネージドポリシーで補う**: AWS の Permission Set 推奨パターンに準拠する。

過度に細分化すると管理負荷が増えるため、初期は粗い粒度で開始し、運用上の課題に応じて細分化する反復的なアプローチが推奨される。

### Q4-3. Break Glass アクセスはどのように設計するか。
A. 一般的な設計は以下のとおり。

1. **専用の Break Glass IAM ユーザーまたはロール**: 通常運用では使用しない。
2. **物理的なクレデンシャル保管**: 金庫または封筒等での物理保管。
3. **多人数承認**: 利用時には複数人の承認を要求。
4. **自動アラート**: 利用が発生した時点で SecurityHub／GuardDuty／CloudWatch Events で即時通知。
5. **事後レビュー**: 利用後 24 時間以内に経緯を記録し、関係者でレビュー。

## 5. セキュリティサービスに関する質問

### Q5-1. 共通基盤として強制すべきセキュリティサービスは何か。
A. 一般的に共通基盤で全アカウント有効化を強制するサービスは以下のとおり。

- **AWS Security Hub**: 検出結果の集約と標準準拠状況の評価
- **Amazon GuardDuty**: 脅威検出
- **AWS Config**: リソース設定の記録と評価
- **AWS CloudTrail**: API コール監査（組織トレイル）
- **AWS IAM Access Analyzer**: 外部アクセス検出

任意で有効化するサービスとして、Amazon Macie（個人情報検出）、Amazon Inspector（脆弱性検出）、Amazon Detective（インシデント調査）などがある。利用システムの特性に応じて選択する。

### Q5-2. Security Hub の Delegated Administrator はどのアカウントに設定するか。
A. 一般的に Audit アカウントを Delegated Administrator に設定する。Management アカウントを Delegated Administrator として使用することは、最小権限の原則および Management アカウントの保護の観点から推奨されない。

### Q5-3. Conformance Pack はどのように活用するか。
A. AWS Config の Conformance Pack は、複数の Config Rules をパッケージ化したものである。金融機関では以下のパックを活用するパターンが一般的。

- **AWS Foundational Security Best Practices**
- **CIS AWS Foundations Benchmark**
- **PCI DSS**（クレジットカード取扱いがある場合）
- **HIPAA**（医療データを扱う場合は対象外）
- **NIST 800-53**

Conformance Pack はイミュータブル（管理アカウントから配布した場合、メンバーアカウントからの改変不可）であるため、例外を扱う場合は別途運用設計が必要となる。

## 6. 規制およびコンプライアンスに関する質問

### Q6-1. FISC 安全対策基準への対応はどのように進めるか。
A. 一般的なアプローチは以下のとおり。

1. **FISC 安全対策基準のうち準拠する版を確定する**（現行は 2025 年 3 月公表の第 13 版）。
2. **AWS FISC 対応リファレンス**（NRI／SCSK／ISID 等のパートナーが共同で作成、第 2 版は 2024 年 8 月発行）を参照する。
3. **FSI Lens for FISC** を AWS Well-Architected Tool にロードして対応状況を評価する。
4. **個別の管理策に対する自社実装のマッピング表** を作成し、監査部門と合意する。

### Q6-2. 金融庁サイバーセキュリティガイドラインへの対応はどのように行うか。
A. 2024 年 10 月公表のガイドラインは 175 項目の対応事項を定めており、以下の領域での対応が必要となる。

- **データ保護**（暗号化、ライフサイクル管理）
- **クラウド対策**（クラウド固有リスクへの対応）
- **サードパーティ管理**（クラウド事業者を含む第三者リスク管理）
- **インシデント対応**
- **業務継続**

2026 年 4 月 3 日公表の金融庁 TPCRM 調査報告書も、第三者リスク管理の実装基準として参照する。

### Q6-3. 監査ログの保管年限はどのように設計するか。
A. 一般的に金融機関では 7 年〜10 年の保管が求められる。設計パターンは以下のとおり。

1. **S3 Standard**: 直近 1 年程度の検索性を確保
2. **S3 Glacier Instant Retrieval ／ S3 Glacier Flexible Retrieval**: 1〜3 年程度の中期保管
3. **S3 Glacier Deep Archive**: 3〜10 年程度の長期保管
4. **S3 Object Lock**: 改ざん防止が必要なログに対して適用

検索基盤として Athena または OpenSearch を併用し、必要に応じてアーカイブから取り出すアーキテクチャを採用する。

### Q6-4. 個人情報保護法および越境移転規制への対応はどのように行うか。
A. 個人情報保護委員会のガイドラインに沿って、以下の観点で設計する。

1. **データの所在**: 東京リージョンまたは大阪リージョンに限定する場合、Region Deny SCP を適用する。
2. **越境移転**: グローバル CDN（CloudFront）等で物理的に海外を経由する場合は、適切な同意取得プロセスを整備する。
3. **クラウド事業者の取扱い**: 個人情報保護委員会のガイドラインにおける「クラウドサービス提供事業者が個人データを取り扱わない場合」の整理を踏まえる。

### Q6-5. 経済安全保障推進法の影響範囲は。
A. 金融機関は特定社会基盤事業者として指定されており、特定重要設備の導入・変更に際して事前届出が必要となる場合がある。クラウド事業者の選定にあたっては、ISMAP 登録の有無や、リスク管理基準への適合性が考慮される。

## 7. IaC・CI/CD に関する質問

### Q7-1. Terraform、CDK、CloudFormation のどれを標準とすべきか。
A. 選定基準は以下のとおり整理できる。

- **Terraform**: マルチクラウド対応、エコシステムの広さ、金融機関での採用実績。一方で AWS の新サービス対応に若干のラグが生じることがある。
- **AWS CDK**: プログラミング言語による表現力、AWS 公式サポートの厚さ。一方でランタイム依存（Node.js）の管理が必要。
- **AWS CloudFormation**: AWS マネージドサービス（Control Tower、LZA）の内部で利用されるため、必然的に併用が発生する。直接記述する場合、テンプレートの記述量が多くなる傾向。

実務上は Terraform を標準とし、Control Tower／LZA の管理範囲は CloudFormation を併用するハイブリッドパターンが多い。

### Q7-2. IaC の静的解析はどのように組み込むか。
A. CI パイプライン上で以下のツールを組み合わせて実行することが一般的。

- **tfsec**: Terraform 向け、セキュリティ設定不備検出
- **Checkov**: マルチクラウド対応、ポリシー違反検出
- **cdk-nag**: AWS CDK 向け
- **cfn-nag**: CloudFormation 向け

検出結果を SARIF 形式で出力し、GitHub Code Scanning に統合する構成も採用される。

### Q7-3. CI/CD の承認ゲートはどのように設計するか。
A. 金融機関では以下の承認ゲートを設けるパターンが一般的。

1. **コードレビュー**: Pull Request の承認（最低 2 名）
2. **ステージング環境へのデプロイ**: 自動
3. **本番環境へのデプロイ**: CAB（Change Advisory Board）承認後に手動承認ゲートを通過

緊急変更については、別経路（Emergency Change）を用意し、事後の CAB レビューを必須とする運用が一般的。

## 8. 監視・運用に関する質問

### Q8-1. 共通基盤の監視はどのように設計するか。
A. 一般的な設計は以下のとおり。

1. **メトリクス**: CloudWatch をベースに、Splunk／Datadog／New Relic 等の外部 SaaS と連携。
2. **ログ**: CloudWatch Logs に集約後、長期保管用に S3 にエクスポート、検索用に OpenSearch または Athena を利用。
3. **トレーシング**: AWS Distro for OpenTelemetry (ADOT) ／ AWS X-Ray を利用。X-Ray は 2026 年 2 月にメンテナンスモードに移行しているため、新規実装は ADOT を推奨。
4. **アラート**: CloudWatch Alarms、Security Hub からの通知を SNS／PagerDuty／Opsgenie 等に配信。
5. **インシデント管理**: AWS Systems Manager Incident Manager または ServiceNow／Jira Service Management。

### Q8-2. SLI／SLO はどのように設定するか。
A. 共通基盤として提供するサービスごとに SLI／SLO を定義する。例として以下を設定する。

- **アカウント発行**: 申請から払い出しまでの所要時間（例：4 時間以内）
- **ネットワーク接続**: TGW を経由した通信のレイテンシ
- **セキュリティアラートの応答**: 検出から初動までの所要時間
- **CI/CD パイプラインの可用性**: デプロイ実行可能率

利用システム側にも SLI／SLO 定義を求め、共通基盤側の SLO は利用システムの SLO を支える前提で設計する。

### Q8-3. インシデント対応の体制はどのように整備するか。
A. 一般的な整備内容は以下のとおり。

1. **オンコール体制**: 24／365 または営業時間内のいずれを採用するか決定する。
2. **エスカレーションマトリクス**: 重大度（Critical／High／Medium／Low）別に通報先と対応 SLA を定義する。
3. **Runbook の整備**: 想定される障害シナリオに対する手順書を整備する。
4. **事後レビュー**: ポストモーテムを実施し、再発防止策を整理する。

## 9. 移行戦略に関する質問

### Q9-1. 7R 戦略の中で、共通基盤側がどの戦略を支援するか。
A. 共通基盤側は以下の戦略を主に支援する。

- **Rehost**: ネットワーク基盤、IAM ベースライン、セキュリティサービスを提供することで、利用システムが最小限の作業で移行できる環境を整備する。
- **Replatform**: マネージドサービス利用（RDS、ECS、Lambda 等）への移行をテンプレートで支援する。
- **Refactor**: 共通基盤の標準サービス（API Gateway、EventBridge、Step Functions 等）の利用を促進する。

Retain（オンプレ残置）については、ネットワーク接続（Direct Connect）の提供に留まる。

### Q9-2. パイロット移行の対象選定基準は。
A. 一般的な選定基準は以下のとおり。

1. **業務影響度が中程度**: 移行で失敗した場合の業務影響が限定的なシステム。
2. **技術的依存関係が少ない**: 他システムとの結合が少ない。
3. **オーナー部門の協力姿勢**: 移行に積極的な部門が所管するシステム。
4. **規模が中程度**: 大きすぎず、小さすぎず、移行ノウハウを蓄積できる規模。

### Q9-3. オンプレと AWS の並行運用期間はどのように設計するか。
A. 並行運用期間中は二重課金が発生するため、以下を事前に決定する必要がある。

1. **並行運用の期間上限**（例: 3 か月、6 か月）
2. **二重課金の予算上限と負担部門**
3. **データ整合性の確認方式**（件数照合、ハッシュ照合、業務照合）
4. **切戻し条件**（並行運用中に AWS 側で重大な問題が発生した場合の判断基準）

## 10. 担当者の経験・適性に関する質問

### Q10-1. AWS マルチアカウント設計の経験を具体的に教えてほしい。
A. これまでに以下のような構成での設計・運用経験を有する。

- AWS Organizations を用いたアカウント分離（環境別、用途別）
- IAM ロールベースのクロスアカウントアクセス設計
- CloudTrail の組織トレイルによる監査ログ集約
- セキュリティサービス（GuardDuty、Security Hub、Config）の集約設計
- SCP による Preventive ガードレールの設計

直近の案件で大規模な Control Tower／LZA の導入経験がない場合は、公式ドキュメントおよび BLEA for FSI を参照しながら習得を継続している旨を補足する。

### Q10-2. FISC 安全対策基準への対応経験は。
A. FISC 安全対策基準そのものに直接対応した案件経験がない場合は、以下のアプローチで補強できる旨を説明する。

- AWS FISC 対応リファレンス（パートナー共同作成）を参照
- FSI Lens for FISC を Well-Architected Tool にロードして評価
- 個別の管理策と AWS 実装のマッピング表を作成

過去に金融業界のセキュリティ要件（PCI DSS 等）への対応経験があれば、その経験を踏まえた類推適用が可能である旨を補足する。

### Q10-3. 既存ベンダー・既存資産との調整経験は。
A. 過去案件で以下のような調整経験を有する旨を伝える。

- 既存オンプレミスベンダーとのネットワーク接続調整
- 既存 IaC 資産（CloudFormation／Terraform）の引継ぎおよび統合
- 既存セキュリティ基準への対応（クライアント独自基準、業界標準）
- 関係者間の合意形成（設計レビュー、ADR 作成）

### Q10-4. 要件定義フェーズにおける役割の認識は。
A. 要件定義フェーズでは、技術的な実装方針を決める前に、以下を整理することが重要と認識している。

1. **ステークホルダー分析**: 誰が何を決め、誰に承認を得るか。
2. **非機能要件の整理**: IPA 非機能要求グレード等を用いた網羅的な整理。
3. **規制要件の取込み**: FISC、金融庁ガイドライン等の管理策と AWS 実装のマッピング。
4. **既存資産との整合方針**: 既存ベンダー・既存資産との関係性整理。
5. **後工程への引き継ぎ資料**: 基本設計、詳細設計、構築の各フェーズで参照可能な形での文書化。

## 11. その他

### Q11-1. プロジェクトで最も気を付けるべき点は何か。
A. クラウド共通基盤プロジェクトで一般的に重要とされる点は以下のとおり。

1. **要件凍結のタイミング**: 要件定義と設計の並走時に、何をもって要件凍結とするかの基準を明確にする。
2. **規制要件の早期取込み**: 後工程で監査部門から指摘されると手戻りが大きいため、要件定義段階で監査部門・セキュリティ部門を巻き込む。
3. **利用部門との合意形成**: 共通基盤の標準（ガードレール、ネットワーク制約等）に対する利用部門の理解と合意を早期に得る。
4. **既存資産との整合**: 既存ベンダーとの関係性を踏まえた、現実的な移行ロードマップを描く。

### Q11-2. 担当領域以外の質問が来た場合、どのように対応するか。
A. 知見が不足している領域については、以下のアプローチで対応する。

1. **正直に「知見が不足している」旨を伝える**: 不確かな回答は避ける。
2. **類似領域での経験を述べる**: 直接の経験がなくても、類推可能な経験がある場合はそれを共有する。
3. **キャッチアップの方針を示す**: 一次資料（公式ドキュメント、リファレンスアーキテクチャ）を参照する旨を伝える。
