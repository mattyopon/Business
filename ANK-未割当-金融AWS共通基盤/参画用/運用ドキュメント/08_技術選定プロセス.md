# 技術選定プロセスドキュメント

## 1. 概要

### 1.1 目的
本ドキュメントは、新規プロダクトや機能追加における技術選定のプロセスと判断基準を定義する。

### 1.2 適用範囲
- 新規サービス/機能のアーキテクチャ設計
- 既存システムの技術スタック変更
- ツール/ライブラリの新規導入

---

### 4.2 ADR 例

> **本 ADR はサンプル（未確定案件のテンプレート例示）であり、実案件で LZA 採用を確定したものではない。**
> 実案件で記入する際は、ステータス・コンテキスト・選択肢の比較結果を案件固有の情報で書き換え、規制要件・既存資産・運用体制を踏まえて評価したうえで決定を確定する。
> 本書のサンプルでは `Proposed`（提案中）ステータスを基本とし、`Accepted` への変更は実案件側の意思決定者の合意を取得したタイミングで行う。

```markdown
# ADR-001: マルチアカウント基盤の構築方式として AWS Landing Zone Accelerator on AWS (LZA) を採用（**サンプル ADR：未確定案件向けのテンプレート例示**）

## ステータス
Proposed（サンプル ADR のため未確定。実案件で意思決定者と合意したうえで Accepted に変更すること）

## コンテキスト
金融機関向けのクラウド共通基盤として、マルチアカウント環境を構築する必要がある。
要件は以下のとおり。

- AWS Organizations 配下で複数アカウントを管理し、OU 単位でガバナンスを適用する
- FISC 安全対策基準・金融庁サイバーセキュリティガイドライン等の規制要件を踏まえる
- 監査ログの一元集約および長期保管が可能
- 標準的なガードレール（SCP、Config Rules、Conformance Pack）を一括展開可能
- 利用部門向けのアカウント発行ワークフローを自動化可能

## 決定（**サンプル：実案件確定前**）
本サンプルでは AWS Landing Zone Accelerator on AWS (LZA) を有力候補として提案する。実案件においては、下記の選択肢比較を案件固有の前提（規制版、既存資産、運用体制、参画フェーズ）で評価したうえで意思決定者の承認を得て確定する。

## 検討した選択肢

### 選択肢 1: AWS Control Tower
**説明**: AWS が提供するマルチアカウント環境構築のマネージドサービス。

**メリット**:
- マネージドな範囲が広く、運用負荷が低い
- 設定が比較的シンプル
- Preventive／Detective／Proactive のコントロールを標準提供

**デメリット**:
- 規制業界特有の拡張要件への柔軟性が限定的
- 既存のカスタム要件との整合に制約が生じる場合がある

### 選択肢 2: AWS Landing Zone Accelerator on AWS (LZA)
**説明**: 規制業界（金融、医療、政府）向けに最適化されたオープンソースの基盤構築フレームワーク。

**メリット**:
- 規制業界向けの構成テンプレートが提供されている
- 柔軟なカスタマイズが可能
- LZA Compliance Workbook により複数フレームワーク統合が容易

**デメリット**:
- Control Tower より初期構築の作業量が多い
- 内部実装が CloudFormation のため、Terraform 中心の運用と併用設計が必要

### 選択肢 3: 独自構築
**説明**: AWS Organizations、SCP、Config 等を組み合わせて独自に構築する方式。

**メリット**:
- 既存資産との整合性を最大化できる
- 自由度が最も高い

**デメリット**:
- 構築・運用の負荷が非常に高い
- 維持メンテナンスのコストが大きい

## 理由
1. **規制対応**: 金融業界の規制要件への対応において、LZA の規制業界向けテンプレートが活用できる
2. **柔軟性**: 既存ベンダー資産との整合性を保ちつつ、追加要件にも対応可能
3. **将来性**: LZA Compliance Workbook 等の拡張機能の継続的な提供が見込まれる

## 結果
- 構築フェーズで LZA の習熟が必要（数週間のキャッチアップ期間）
- 内部の CloudFormation と利用者側の Terraform を併用する設計指針を別途整備
- 規制対応の根拠資料が AWS 公式ドキュメントとして揃う

## 参考資料
- [Landing Zone Accelerator on AWS](https://aws.amazon.com/solutions/implementations/landing-zone-accelerator-on-aws/)
- [AWS Control Tower User Guide](https://docs.aws.amazon.com/controltower/latest/userguide/)
- [AWS 金融リファレンスアーキテクチャ日本版（GitHub）](https://github.com/aws-samples/baseline-environment-on-aws-for-financial-services-institute)
```

## 6. 技術選定ガイドライン

### 6.1 推奨技術スタック

| カテゴリ | 推奨 | 代替 | 備考 |
|---------|------|------|------|
| コンテナオーケストレーション | EKS (Fargate) | ECS | 大規模・複雑な場合はEKS |
| データベース | Aurora MySQL | RDS MySQL | 高可用性要件ならAurora |
| キャッシュ | ElastiCache (Redis) | DynamoDB DAX | セッション、キャッシュ用途 |
| メッセージキュー | SQS | Kafka (MSK) | ストリーミング要件ならKafka |
| CI/CD | GitHub Actions | CodePipeline | GitHub利用の場合 |
| IaC | Terraform | CloudFormation | マルチクラウド考慮 |
| 監視 | Prometheus + Grafana | CloudWatch | K8s環境ならPrometheus |

### 6.2 避けるべきアンチパターン

| アンチパターン | 問題 | 推奨 |
|---------------|------|------|
| 新技術の早期採用 | 安定性・サポート不足 | GA後1年以上経過したものを選定 |
| 過度なマイクロサービス | 運用複雑化 | 適切な粒度で分割 |
| 自前実装 | 車輪の再発明 | マネージドサービス活用 |
| ベンダーロックイン | 将来の柔軟性欠如 | 抽象化レイヤーを設ける |

## 7. レビュー・承認プロセス

### 7.1 レビュー観点

| 観点 | チェック項目 |
|------|-------------|
| 技術的妥当性 | 要件を満たすか、オーバースペックでないか |
| セキュリティ | 脆弱性、コンプライアンス対応 |
| コスト | 予算内か、隠れコストはないか |
| 運用性 | 既存運用体制で対応可能か |
| チーム対応 | 必要スキルは確保できるか |

### 7.2 承認フロー

```
提案者 → アーキテクトレビュー → セキュリティレビュー → Tech Lead承認
           (技術評価)            (セキュリティ評価)      (最終判断)
```

### 7.3 承認基準

| 影響範囲 | 承認者 | 所要日数目安 |
|---------|--------|-------------|
| 局所的（1サービス） | アーキテクト | 3日 |
| 中規模（複数サービス） | Tech Lead | 1週間 |
| 大規模（プラットフォーム全体） | CTO | 2週間 |
