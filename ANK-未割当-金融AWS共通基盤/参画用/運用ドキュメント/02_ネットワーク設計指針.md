# 02. ネットワーク設計指針

本書は、金融機関向け AWS クラウド共通基盤におけるネットワーク設計の指針をまとめたものである。

---

## 1. 設計方針

- 専用線（AWS Direct Connect）による安定したオンプレミス接続
- ハブ＆スポーク型のマルチ VPC 構成（Transit Gateway 利用）
- 集中型 Egress による外向き通信の統制
- VPC エンドポイント／PrivateLink による AWS サービス内部接続
- IP アドレス計画に基づく拡張性の確保

---

## 2. リージョン構成

### 2-1. 主リージョン

- ap-northeast-1（東京）を主リージョンとする。

### 2-2. DR リージョン

- ap-northeast-3（大阪）を DR リージョンとして検討する。
- DR 戦略は Backup & Restore／Pilot Light／Warm Standby／Multi-Region Active-Active の中から、業務特性に応じて選択する。

---

## 3. オンプレミス接続

### 3-1. Direct Connect

- 帯域: 業務特性に応じて 1Gbps／10Gbps から選択
- 冗長: 異なる DX Location（最低 2 拠点）からの専用線
- キャリア: 異なる通信事業者を経由する構成を推奨
- バックアップ: AWS Site-to-Site VPN によるバックアップ経路

### 3-2. Direct Connect Gateway

- 複数リージョン・複数アカウントの VPC を Direct Connect 経由で接続するための Direct Connect Gateway を Network アカウントに配置

---

## 4. VPC 構成

### 4-1. CIDR 計画

- 全社で利用可能な CIDR レンジを確保する（例：10.0.0.0/8 のうち特定セグメント）
- 環境別・事業部別に CIDR を割り当てる
- オンプレミス側の CIDR との重複を回避

### 4-2. サブネット構成

- 各 AZ にパブリックサブネット、プライベートサブネット、データベース用サブネットを配置
- マルチ AZ 構成を前提とする
- VPC Flow Logs を有効化し、Log Archive アカウントに集約

### 4-3. VPC タイプ

- Workloads VPC: 利用システムが配置される VPC
- Egress VPC: 外向き通信を集約する VPC（Network アカウント配置）
- Inspection VPC: トラフィック検査を行う VPC（Network Firewall 配置）
- Endpoint VPC: VPC エンドポイントを集約する VPC

---

## 5. Transit Gateway

### 5-1. 配置

- Network アカウントに Transit Gateway を配置
- AWS Resource Access Manager (RAM) で他アカウントの VPC に共有

### 5-2. ルーティング

- ルートテーブルを用途別に分離（共通アクセス用、隔離用、Inspection 経由用）
- 必要に応じて attachment ごとの propagation／association を制御

---

## 6. 集中型 Egress

### 6-1. AWS Network Firewall

- Inspection VPC に AWS Network Firewall を配置
- 全 VPC からの外向き通信を Transit Gateway 経由で Inspection VPC に集約
- TLS Inspection が必要な場合は、利用可能なリージョン・サービスを別途確認

### 6-2. NAT Gateway

- Egress VPC に NAT Gateway を配置
- 各 Workloads VPC は NAT Gateway を直接持たず、Transit Gateway 経由で Egress VPC に向ける

---

## 7. VPC エンドポイント／PrivateLink

### 7-1. 集約方針

VPC エンドポイントは **Gateway 型** と **Interface 型** で集約可否が異なる点に注意して設計する。

- **Gateway Endpoint (S3／DynamoDB)**: ルートテーブル経由でしか機能せず、Transit Gateway や VPC Peering を経由して他 VPC からは利用できない。したがって **Endpoint VPC への集約は不可** であり、利用が必要な各 Workloads VPC で個別に Gateway Endpoint を作成する。ゲートウェイ型のため追加料金は発生せず、各 VPC での作成は運用負荷の観点でも問題にならない。
- **Interface Endpoint (KMS／Secrets Manager／CloudWatch Logs／STS／SSM／ECR 等の AWS PrivateLink 系)**: Endpoint VPC に集約する。Interface Endpoint は時間課金＋データ処理課金が発生するため、集約による単価最適化と監査一元化の効果が大きい。**ただし AWS マネージドな Private DNS は Endpoint VPC でしか機能しない (TGW / Peering 経由の Spoke VPC からは標準 DNS 名が public IP に解決されてしまう)** ため、**集中型 Interface Endpoint では「Endpoint 側の Private DNS を無効化」+「サービスごとに Route 53 Private Hosted Zone (例: `kms.ap-northeast-1.amazonaws.com`) を自前で作成」+「その PHZ を全 Workloads VPC に associate して Endpoint の DNS 名を指す A/CNAME を登録」の 3 点セットで配信する**。または Route 53 Resolver Inbound/Outbound Endpoint を Endpoint VPC に置き、Spoke 側の Resolver を Conditional Forwarding で接続する代替案を採る。Endpoint の Private DNS を有効にしたまま PHZ "共有" だけで済ますパターンは成立しないので採用しないこと。

### 7-1-2. 構成図（イメージ）

```
[Workloads VPC] --(Gateway Endpoint)--> S3 / DynamoDB           # 各 VPC で個別
[Workloads VPC] --TGW--> [Endpoint VPC] --(Interface Endpoint)--> KMS / SM / Logs / STS / SSM / ECR
```

### 7-1-3. 設計上の注意点

- Gateway Endpoint のルートテーブル更新は Workloads VPC のルートテーブルに対して行う。Endpoint VPC のルートテーブルには載せない。
- 集中型 Interface Endpoint では、Endpoint 側の AWS マネージド Private DNS は **無効化** すること (有効のままだと Spoke VPC からは public エンドポイントに解決されてしまい、集約 Interface Endpoint が使われない)。代わりに Route 53 Private Hosted Zone を自前で立て、全 Workloads VPC に associate する運用にする。
- 監査要件として AWS PrivateLink を通る通信のログが必要な場合は、Endpoint VPC 側で VPC Flow Logs を有効化する。

### 7-2. PrivateLink

- 外部 SaaS（Splunk、Datadog 等）への接続は PrivateLink を採用
- インターネット経由を回避することで、データの安全性と監査性を向上

---

## 8. AWS WAF および Shield Advanced

### 8-1. AWS WAF

- インターネット公開する Web アプリケーションには WAF を適用
- AWS マネージドルールセット（AWSManagedRulesCommonRuleSet、AWSManagedRulesSQLiRuleSet 等）の利用
- レートベース制限の設定

### 8-2. AWS Shield Advanced

- ミッションクリティカルなシステムに対して採用を検討
- Shield Response Team (SRT) のサポートを利用可能

---

## 9. IP アドレス管理

- IP アドレスの払い出しは Network アカウントで一元管理
- IPAM (IP Address Manager) を活用した自動化を検討
- 払い出し記録、未使用 CIDR の棚卸しを定期的に実施
