# 01. マルチアカウント設計指針

本書は、金融機関向け AWS クラウド共通基盤におけるマルチアカウント設計の指針をまとめたものである。AWS 公式リファレンスおよび AWS 金融リファレンスアーキテクチャ日本版に基づいて整理している。

---

## 1. 目的

- アカウント単位での明確な境界に基づくガバナンスの確立
- 業務領域・環境・セキュリティ境界別のリスク分散
- 規制要件（FISC、金融庁ガイドライン）への対応に必要な分離設計
- スケーラブルなアカウント発行および運用の実現

---

## 2. 採用方針

### 2-1. ベース技術

以下のいずれかを採用する。選定基準は要件定義時に整理する。

| 選択肢 | 特徴 | 適合する状況 |
|--------|------|--------------|
| AWS Control Tower | マネージドな範囲が広く運用負荷が低い | 標準的なガードレールで足りる場合 |
| AWS Landing Zone Accelerator (LZA) | 規制業界向けに最適化、柔軟性高い | 金融機関の独自要件が多い場合 |
| 独自構築 | 自由度最大 | 既存資産との整合性を最優先する場合 |

### 2-2. リファレンスアーキテクチャの参照

- AWS 金融リファレンスアーキテクチャ日本版（最新版 v1.6）の構成を出発点として参照する。
- BLEA for FSI（Baseline Environment on AWS for Financial Services Institute）の CDK 実装をベースとして検討する。

## 3. OU 設計

### 3-1. 標準 OU 構成

| OU | 用途 |
|----|------|
| Security OU | Log Archive アカウント、Audit アカウント |
| Infrastructure OU | 共通ネットワーク、共有サービス |
| Workloads OU | 本番／ステージング／開発の各アカウント |
| Sandbox OU | 実験用アカウント |
| PolicyStaging OU | ポリシー変更の事前検証 |
| Suspended OU | 利用停止アカウント |

### 3-2. Workloads OU の階層化

事業部別・環境別の階層化を検討する。例：

```
Workloads OU
├── BusinessUnitA OU
│   ├── Prod OU
│   ├── Staging OU
│   └── Dev OU
├── BusinessUnitB OU
│   ├── Prod OU
│   ├── Staging OU
│   └── Dev OU
```

階層化により、SCP の継承および権限委譲を組織構造に沿って実現できる。

## 4. 共通アカウントの役割

| アカウント | 役割 |
|------------|------|
| Management | AWS Organizations および請求の管理 |
| Log Archive | 全アカウントのログ集約（CloudTrail、Config、VPC Flow Logs 等） |
| Audit | セキュリティサービスの Delegated Administrator（Security Hub、GuardDuty 等） |
| Network | Transit Gateway、Direct Connect、共通ネットワーク基盤 |
| Shared Services | 共通サービス（ECR、CodeArtifact、IAM Identity Center 等） |

Management アカウントへの直接アクセスは Break Glass を除き原則禁止とする。

---

## 5. アカウント発行ワークフロー

### 5-1. 発行ツールの選定

| ツール | 特徴 |
|--------|------|
| Account Factory for Terraform (AFT) | GitOps スタイル、Terraform 習熟チーム向け |
| AWS Service Catalog | 承認済みリソーステンプレートの提供 |
| ServiceNow Service Management Connector | 既存 ServiceNow 運用との統合 |

### 5-2. 発行プロセス

1. 利用部門からの申請
2. 共通基盤チームによる審査（命名規則、用途妥当性、予算上限）
3. 自動払い出し（AFT または Service Catalog 経由）
4. IAM ベースラインの適用
5. ネットワーク接続の構成
6. 利用部門への引き渡し

申請から払い出しまでの SLA は要件定義時に決定する。

---

## 6. ガードレール

### 6-1. 種別

- **Preventive（SCP）**: 未然防止
- **Detective（Config Rules、Security Hub）**: 検出
- **Proactive（CloudFormation Hooks）**: 事前検証

### 6-2. カテゴリ

- **Mandatory**: 全アカウントで強制適用
- **Strongly Recommended**: 強く推奨、適用除外には承認が必要
- **Elective**: 選択適用

### 6-3. 標準ガードレールの例

- Region Deny（東京リージョン以外の利用を制限）
- Root ユーザーの API 利用禁止
- CloudTrail の無効化禁止
- Config の無効化禁止
- 公開 S3 バケットの禁止（個別承認が必要な場合のみ例外）

---

## 7. 例外申請プロセス

ガードレールへの例外申請は以下のプロセスとする。

1. 利用部門からの申請（理由、影響範囲、期間）
2. 共通基盤チームによる技術評価
3. セキュリティ部門による承認
4. 期限付きの例外適用（恒常的な例外は別途審議）
5. 期限到来時の自動失効通知
