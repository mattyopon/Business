# 04. セキュリティサービス設計指針

本書は、金融機関向け AWS クラウド共通基盤におけるセキュリティサービスの設計指針をまとめたものである。

---

## 1. 設計方針

- 共通基盤で標準サービスを強制有効化
- Audit アカウントに Delegated Administrator を集約
- SIEM 連携を前提とした検出ログの統合管理
- 監査・コンプライアンス対応に必要な証跡の長期保管

---

## 2. 強制有効化するセキュリティサービス

| サービス | 用途 | 委任先 |
|----------|------|--------|
| AWS Security Hub | 検出結果の集約、標準準拠状況評価 | Audit |
| Amazon GuardDuty | 脅威検出（CloudTrail、VPC Flow Logs、DNS） | Audit |
| AWS Config | リソース設定の記録、ポリシー評価 | Audit |
| AWS CloudTrail（組織トレイル） | API 監査 | Management（出力先は Log Archive） |
| AWS IAM Access Analyzer | 外部アクセスの検出 | Audit |

---

## 3. 任意有効化のセキュリティサービス

| サービス | 用途 | 採用基準 |
|----------|------|----------|
| Amazon Macie | S3 内の機密データ検出 | 個人情報・機密情報を扱う S3 がある場合 |
| Amazon Inspector | 脆弱性検出（EC2、Lambda、ECR） | 自社管理のコンピューティングリソースが多い場合 |
| Amazon Detective | インシデント調査支援 | GuardDuty 検出が多く調査負荷が高い場合 |
| AWS Audit Manager | 監査証跡の自動収集 | 監査対応の自動化を行う場合 |

---

## 4. Security Hub の活用

### 4-1. 有効化する標準

- AWS Foundational Security Best Practices
- CIS AWS Foundations Benchmark
- PCI DSS（クレジットカード取扱いがある場合）
- NIST 800-53（必要に応じて）

### 4-2. 検出結果の管理

- Critical／High の検出は即時通知（SNS → PagerDuty／Slack）
- Medium／Low は週次レビュー
- 抑制ルール（Suppression）の運用基準を定義
- 検出件数の月次トレンドの可視化

---

## 5. GuardDuty の活用

### 5-1. 有効化範囲

- 全アカウント、全リージョン
- 新規アカウント発行時の自動有効化

### 5-2. 検出種別

- 通常のシグナル（不審な API 利用、マルウェア通信 等）
- S3 Protection（S3 アクセスの異常検出）
- Malware Protection（EBS、ECR）
- RDS Protection（RDS ログイン異常）
- EKS Protection（クラスター異常）
- Lambda Protection

---

## 6. Config の活用

### 6-1. 記録対象

- 全リソースタイプを対象（必要に応じて除外設定）
- グローバルリソース（IAM 等）は単一リージョンで記録

### 6-2. Conformance Pack

- FISC 対応（FSI Lens for FISC 等で対応マッピング）
- CIS AWS Foundations Benchmark
- PCI DSS（該当する場合）
- NIST 800-53

### 6-3. 修復

- 自動修復が可能なルール: AWS Systems Manager Automation 経由
- 手動修復が必要なルール: チケット化して対応
- 修復不可（情報のみ）: 月次レビューで承認または無視判断

---

## 7. CloudTrail の設計

### 7-1. 組織トレイル

- Management アカウントから組織トレイルを設定
- 全アカウント、全リージョン、データイベント（必要に応じて）を取得
- 出力先は Log Archive アカウントの S3 バケット

### 7-2. 保管設計

- S3 Object Lock（コンプライアンスモード）による改ざん防止
- 保管年限は規制要件に基づく（一般に 7〜10 年）
- ライフサイクル設定により Standard → Glacier Flexible Retrieval → Glacier Deep Archive

### 7-3. 検索性の確保

- Athena テーブルを作成し、SQL でクエリ可能にする
- OpenSearch との連携（必要に応じて）

---

## 8. WAF および Shield Advanced

### 8-1. AWS WAF

- インターネット公開する Web アプリケーションに適用
- AWS マネージドルール（Common、SQLi、Linux、Unix、IP Reputation 等）
- レートベース制限
- カスタムルール（業務固有のブロック条件）

### 8-2. AWS Shield Advanced

- ミッションクリティカルな対象に適用
- AWS DDoS Response Team (DRT) のサポート

---

## 9. 暗号化および鍵管理

### 9-1. AWS KMS

- カスタマーマネージドキー (CMK) を標準
- キーのローテーションを有効化（年次）
- アカウント別／用途別にキー分離
- キーポリシーで最小権限を強制

### 9-2. AWS CloudHSM／External Key Store

- FISC 等の規制要件で HSM が必須となる場合に採用
- 鍵のライフサイクル管理（生成・利用・廃棄）を明文化

### 9-3. データ保護

- 転送時: TLS 1.2 以上
- 保存時: S3 SSE-KMS、EBS 暗号化、RDS 暗号化（全て CMK 利用）
- バックアップ・スナップショットの暗号化必須

---

## 10. SIEM 連携

### 10-1. 連携パターン

- Splunk 連携: Kinesis Data Firehose 経由
- Datadog 連携: Datadog Forwarder（Lambda）経由
- AWS Native SIEM: OpenSearch を活用

### 10-2. ログ種別

- CloudTrail
- VPC Flow Logs
- DNS Logs（Route 53 Resolver）
- ALB／NLB アクセスログ
- WAF ログ
- Security Hub findings
- GuardDuty findings
- Config configuration items／compliance change

---

## 11. インシデント対応

### 11-1. 検出から対応までの流れ

1. 検出（Security Hub／GuardDuty／Config 等）
2. 通知（SNS → PagerDuty／Slack）
3. 初動対応（Runbook に従う）
4. 隔離（必要に応じて IAM 権限剥奪、Security Group 変更）
5. 調査（Detective、CloudTrail）
6. 復旧
7. 事後レビュー（ポストモーテム）

### 11-2. AWS Systems Manager Incident Manager

- インシデント管理プロセスの統合
- 関係者への自動通知
- 対応履歴の記録
